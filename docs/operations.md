## Deployment configuration

| Item                     | Current convention               |
| ------------------------ | -------------------------------- |
| Website                  | `https://yutaozhou.com/finance/` |
| Source branch            | `main`                           |
| Static deployment branch | `gh-pages`                       |
| Build directory          | `dist/`, generated by Vite       |
| Vite base                | `/finance/`                      |
| Deployment command       | `npm run deploy`                 |

The publication path is `main` source → local build → `gh-pages` branch → GitHub Pages. The repository has no briefing-generation/deployment GitHub Actions configuration. The platform's Pages deployment job is separate from generating new reports.

## Publish the site

### 1. Synchronize the source

Check the working tree, confirm that you are on `main`, and preserve existing work before updating. Run these commands only in a working tree that can safely be updated; do not use resets or force pushes to overwrite other work.

```bash
git status --short
git branch --show-current
git pull --ff-only origin main
```

Automated content updates may already have pushed new reports. Deploying from an old checkout can restore an outdated content snapshot even when your own UI changes are current.

### 2. Make and validate the change

- For new or corrected briefings, follow [Report data](report-data.md).
- For service arrangements or release notes, follow [Site announcements](site-announcements.md).
- For frontend changes, check the source and affected interactions.

```bash
npx eslint src
npm run build
npm run preview
```

Open the printed `/finance/` preview URL. Check the latest report, the target historical edition and the change itself. Stop the foreground preview server with `Ctrl+C`.

### 3. Commit the source

Stage only the files needed for this change. For a new briefing, replace the example date below with the actual date:

```bash
git add data/2026-11-13.json
git diff --cached --check
git diff --cached --stat
git commit -m "Add daily market insight for 2026-11-13"
git push origin main
```

Use the relevant file list and commit message for UI, announcement or documentation changes. Do not commit `dist/` to `main` or stage unrelated workspace files.

### 4. Publish static files

```bash
npm run deploy
```

This runs `npm run build && gh-pages -d dist` and pushes the generated files to the remote `gh-pages` branch. It requires Node.js, installed dependencies and working Git push access.

`Published` means the deployment branch was pushed. **Wait for the GitHub Pages deployment to finish as well.** A normal `git push origin main` does not replace this step.

### 5. Verify production

1. In the repository's Actions tab, confirm that this `pages build and deployment` job succeeded. If needed, check the publishing source under Settings → Pages.
2. Open production, refresh, and check the target feature, latest report date, target historical edition and main links.
3. If the page still looks old, compare its `assets/index-*.js` / `assets/index-*.css` filenames with this build's `dist/index.html` to distinguish a pending deployment from a local cache issue.
4. Check `git status --short` for unexpected source changes.

A local build or `Published` message alone does not verify that production has updated.

## Documentation-only updates

For changes limited to README files, `docs/`, CONTRIBUTING or CHANGELOG, validate links and examples, then commit and push `main`. These files are not bundled as website pages and normally do not require `npm run deploy`.

`CHANGELOG.md` is a repository history, not an automatic source of reader-facing announcements. To display a notice on the website, edit `src/data/announcements.js` and deploy.

## Failure recovery and rollback

| Situation                             | Response                                                                                                          |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Build fails                           | Preserve source changes and diagnose the error; do not publish incomplete output or edit `dist/` directly         |
| Git push is rejected                  | Review remote commits, synchronize and resolve conflicts using the project workflow, then push; do not force push |
| Source is pushed but deployment fails | Fix network, access or build issues and retry `npm run deploy` from the verified source                           |
| Pages job fails                       | Inspect that job's logs, fix the cause and publish again                                                          |
| Shipped code must be withdrawn        | Identify the problematic commit, create a revert using `git revert`, check the build, push `main` and redeploy    |
| Published report needs correction     | Correct that date's JSON, verify the content and publish; explain significant corrections                         |

Before reverting, inspect the scope with `git log --oneline` and `git show`. New briefings may have landed after the feature commit. Reverting the whole tree or deploying an old build can remove those reports too. Revert the specific problematic change when current reports must be preserved.

## Pause and resume publication

### Before a pause

1. Publish a service notice describing expected timing, affected publication and content that remains accessible. State that dates are unconfirmed when necessary.
2. Use `pinned: true` and `banner: true` for important arrangements. Describe the service impact without publishing private travel or device details.
3. Deploy and verify the live banner and notice before stopping the external generation task.

GitHub Pages hosts published content. Stopping generation does not shut down the site or create new reports. Exact dates for the planned January 2027 pause are not confirmed; consult the actual [announcement data](../src/data/announcements.js).

### When resuming

1. Verify that the external generation process and latest report are working. Check dates, information cutoffs, sources and quote references first.
2. Give the resumption notice a new stable ID so it becomes a new unread message.
3. Remove `banner` / `pinned` from the old pause notice, keep the historical entry and explain that arrangements changed.
4. Deploy and verify the reports and announcements in production. The app does not resume on a calendar date or clear an old banner automatically.

## Automation boundary

`scripts/stocks-morning-brief.ps1` uses hard-coded example prices and writes Markdown to machine-specific paths. It does not generate the `data/YYYY-MM-DD.json` required by the website. `crontab.txt` contains commented examples, not an installed schedule; it does not establish production execution times.

The repository does not implement complete quote collection, AI generation, credentials, scheduling or failure alerts. When maintaining the external process, separately document its actual environment, entry point, named time zone, log location and owner. Keep credentials out of the frontend and documentation. Use named zones such as `America/New_York` or `America/Los_Angeles` rather than applying fixed EST/PST-to-UTC offsets year-round.
